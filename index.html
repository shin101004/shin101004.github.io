CASE 01

잘못된 UX 설계,
14가지 개선안을 제시했습니다.

사용자의 Core Action을 방해하는 잘못된 UI/UX를 발견했습니다. 대형 서비스와 비교하며 근거를 만들고, 일부 화면에서 방향을 먼저 반영한 뒤 제안·명세·개발로 연결했습니다.

VERSUS · 2025—2026
평균 9% → 16% 일간 평균 Core Action 전환 수
12 / 14 UX 개선안 채택 · 14개 제안

    Core Action을 방해하는 UI/UX

    Beta 출시 전후의 화면은 같은 정보가 여러 위치에 반복될 뿐만 아니라, 불필요한 정보가 너무 크게 강조되고 있었습니다. 사용자가 서비스 내에서 제공받아야 할 Core Action까지는 여러 단계를 거쳐야 한다는 점을 문제로 인지하게 되었습니다.
    팀에서 별도 문제로 다루기 전이었지만, 빠르게 개선을 할 필요가 있다고 생각했습니다.

CASE 02

메시지가 쌓여도 빠르게 이어지는
채팅 UX를 만들었습니다.

같은 채팅 화면에서 발생했지만 원인은 달랐습니다. 메시지가 쌓일수록 Query·State Update·Rendering 비용이 커졌고, Room Entry에서는 Member·Read State Sync가 반복됐습니다. 두 Pipeline을 나눠 측정하고 Data Range와 Execution Timing을 각각 다시 설계했습니다.

NEPTO · 2023—2025
10–20ms Message Rendering · 기존 약 300–400ms
0.69ms 신규 메시지 Room Entry · 기존 300.08ms
O(n) → O(1) 표시 속성 계산 · Full List → Insertion Point
  1. Problem

    같은 느림처럼 보였지만 원인이 다른 두 병목

    대용량 DM에서는 Full Message List를 읽은 뒤 일부만 Rendering하는 비용으로 화면이 멈추거나 앱이 종료됐습니다. 반면 채팅방 입장 지연은 방마다 공통 Member·Read State Sync를 다시 실행하는 구조에서 발생했습니다.

  2. Profiling

    Query·Rendering과 Room Entry 비용을 분리

    DB Query, UI State Update, List Rendering, Member·Read State Computation의 실행 시간을 나눠 측정했습니다. Message 수에 따라 커지는 Rendering 비용과 입장할 때마다 반복되는 공통 Sync가 별개의 병목임을 확인했습니다.

  3. Rendering

    필요한 Message Range만 조회하고 다시 계산

    Rendering은 다른 개발자와 방향과 범위를 나눠 개선했습니다. Initial Load·Previous·Latest마다 필요한 Range만 Cursor-based Query로 가져와 Store에 Merge하고, Insertion Point와 Page Boundary 주변만 재연산했습니다.

  4. Room Entry

    공통 Sync를 App Lifecycle로 이동

    채팅방에 입장할 때마다 실행되던 Member·Read State Sync를 App Launch·Foreground Transition·Socket Event 시점으로 옮겼습니다. Room Entry에서는 RealmDB에 반영된 현재 State로 Message Load를 바로 이어가도록 구현했습니다.

  • TypeScript
  • Realm DB
  • Zustand
  • Socket
  • FlashList

  • Before 약 300–400ms
  • After 약 10–20ms
  • Query unit 최신 20개부터
Message rendering shift

Before · DB → state → rendering

Full Room Query · Sort → UI State에서 Slice

Previous·Latest·Target Message Navigation이 하나의 Query Result를 다시 Filter했고, 한 번의 Load에도 Cursor와 List State가 함께 Update됐습니다.

After · DB → store → rendering

User Action → Range Query → Store Merge

Initial Load·Previous·Latest·Target Message Navigation을 분리하고, 각 시점에 필요한 Range만 DB에서 읽어 UI Data로 구성했습니다.
Room entry shift

Before · Every room entry

Room Initialize → Member Sync → Message Load

Left Member와 Member별 Read Cursor를 매번 Query했습니다. 모든 Async Task가 끝난 뒤 ReadCount를 Update해 Room Entry가 Sync Duration의 영향을 받았습니다.

After · Lifecycle and socket

App Lifecycle Sync → Room Entry에서 Current Cursor 사용

공통 Member Sync는 App Launch와 Foreground Transition으로 옮겼습니다. Socket Event 수신 시 사용자별 last_read_message_id를 갱신했습니다.

  • With new message 300.08 → 0.69ms

최신 메시지가 아래에 놓이는 Inverted List에서 Previous와 Latest 방향을 모두 탐색해야 했습니다. 여기에 Realtime Insertion, Reply·Link Preview·Image처럼 Render 이후 높이가 바뀌는 Message가 동시에 Scroll Position에 영향을 줬습니다.

02 · Diagnosis

프로파일링을 통해 Query·State·Rendering으로 분해

Profiling 결과를 DB Query, UI State Update, List Rendering 단계로 나눠 확인했습니다. Full Message List를 먼저 읽고 일부만 사용하는 흐름과, 한 번의 Load에서 여러 State가 연쇄 Update되는 범위를 우선 개선 대상으로 정했습니다.

03 · Query boundary

네 가지 Navigation Intent를 독립된 Query로 분리

Initial Load는 최신 20개, 위로 Scroll하면 Previous Range, 아래로 이동하면 Latest Range를 Query하도록 분리했습니다. Search나 Notification에서 Target Message로 이동할 때는 기준 Message의 앞뒤를 각각 Query해 List를 재구성했습니다.

04 · State boundary

Component State 대신 Store를 Single Source로 사용

DB의 Full Query Result를 Component State에서 Slice하는 대신, Action별 Query Result를 Store에 Merge한 뒤 UI가 Subscribe하도록 바꿨습니다. Query Intent와 State Update Path가 맞물리면서 Update 대상을 Current List Range로 제한할 수 있었습니다.

05 · Room entry boundary

반복되던 공통 Sync를 App Lifecycle로 이동

Left Member와 Member별 Read Cursor Sync는 App Launch와 Foreground Transition에서 실행했습니다. Room Entry에서는 DB에 반영된 Cursor로 ReadCount를 Update하고 Message Load를 이어갔습니다.

06 · Read state model

UI의 ReadCount를 Cursor와 Event Rule로 계산

모든 Message를 읽은 State라면 숫자를 표시하지 않았습니다. Unread State라면 Room Member 수에서 해당 Message의 read_count를 뺀 값을 표시했습니다.

07 · Read event policy

Message Event마다 Read State Policy를 명시

  • Outbound Message는 Sender가 읽은 State이므로 read_count를 1로 생성했습니다.
  • Text·Image Message를 수신하면 Sender를 포함해 read_count를 2로 생성했습니다.
  • 1:1 DM은 Message 수신 시 Current Room을 보고 있으면 Read Complete로 전환했습니다.
  • 그룹 DM은 read_count가 멤버 수와 같아지면 Read Complete로 전환했습니다.
  • Read Receipt Event의 Room·User·Last Message ID로 Room DB의 User Cursor를 Update했습니다.
  • Current Room이라면 DB와 Store를 함께 Update했습니다. 다른 방이라면 DB만 갱신했습니다.
08 · Membership policy

Member Join·Leave 전후에도 ReadCount Semantics를 유지

  • Invited User의 Initial Cursor는 초대 직전 Message로 설정했습니다.
  • 초대 이전 Message는 New Member가 읽은 것으로 보고 read_count를 1씩 더했습니다.
  • Leave Event 자체는 Last Read Cursor로 저장하지 않았습니다.
  • Left User의 기존 Cursor 이전 Message는 read_count를 1씩 줄였습니다.
  • Current Room이라면 Store와 DB를 함께 Update했습니다. 다른 Room이라면 DB만 Update했습니다.
  • ReadCount Recalculation을 마친 뒤 Left User를 Room Data에서 제거했습니다.
09 · Scroll stability

Bidirectional Load 중에도 Scroll Position을 유지

공통 양방향 리스트가 maintainVisibleContentPosition을 소유하도록 감싸고 외부 Override를 Type Level에서 막았습니다. Latest Page이고, 더 불러올 Latest Data가 없으며, 사용자가 Bottom에 있을 때만 Auto Scroll하도록 세 조건을 함께 확인했습니다.

10 · Render policy

Changed Message와 Boundary만 Recalculate

Date Chip, 연속 발화의 Avatar·Timestamp처럼 Neighbor Message에 의존하는 Derived State는 Full List 대신 Insertion Point 주변 최대 3개와 Page Boundary 2개만 Recalculate했습니다. Message Component는 UI에 영향을 주는 Field만 비교해 Re-rendering 범위를 제한했습니다.

11 · Interaction details

Scroll Frame과 UI State Update를 분리

  • 매 Frame 바뀌는 Scroll Offset은 Subscriber를 깨우지 않도록 저장하고, Button Visibility나 Bottom State가 실제로 바뀔 때만 State를 Update했습니다.
  • ‘Move to Latest’ Button은 Show Threshold와 Hide Threshold를 다르게 둬 Boundary 부근에서 반복적으로 깜빡이지 않게 했습니다.
  • ReadCount처럼 짧은 시간에 여러 번 변하는 값은 Memo Comparator에 명시해, Update가 필요한 Message는 놓치지 않도록 했습니다.
  • Initial Render Count·Window Size·Batch Render Count· Viewability Config를 Chat Domain에 맞춰 조정했습니다.
12 · Outcome

Full List가 아니라 Active Range에 비용을 맞춤

Query Range는 사용자가 보고 이동하는 Message Range로 좁혔습니다. Room Entry의 공통 Sync는 App Lifecycle로 이동했습니다. 동일한 Measurement Environment에서 Message Rendering Time은 약 300–400ms에서 10–20ms 수준으로 줄었습니다.

의도적으로 남겨 둔 개선 과제
