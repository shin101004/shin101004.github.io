CASE 04 · ALOCADOS · Developer experience

아무도 맡지 않던 레거시를, 아무도
손대지 않는 자동화로 바꿨습니다.

코드에서는 i18n Key를 사용하고, 번역 문구는 Google Sheets에서 관리하는 협업 구조였습니다. 세 차례의 마이그레이션 동안 두 Source의 변경 시점이 어긋나거나 번역 누락·미사용·중복 Key가 쌓여가고 있었지만, 어느 한 팀의 업무로 남겨두기에는 리소스 낭비라는 생각이 들었습니다. Source Code를 AST로 읽어 Sheet와 교차 검증하고, 발견한 불일치를 안전하게 정리하는 공용 CLI와 GitHub Actions Workflow를 만들었습니다.

  • Adoption8개 프로젝트 적용동일한 검증 규격을 재사용
  • Source analysisAST 기반 Key 추출실제 i18n 호출만 분석
  • ReportKey + Source Path수정 위치까지 함께 전달
  • MaintenanceWorkflow 실행정리 작업을 반복 가능하게 구성
Starting point

문제는 한 팀의 실수가 아니라, 두 Source가 분리된 구조에서 시작됐습니다.

개발팀은 t("key")로 문구를 호출하고, 디자인·번역 담당자는 Sheet에서 Key와 문구를 관리했습니다. Code와 Sheet는 각각 변경될 수 있었고, Sheet가 바뀔 때마다 변경된 내용에만 표시를 남겨 확인하는 번거로운 절차를 거쳐야 했습니다. 수동 확인은 현재 상태를 한 번 맞출 수는 있어도, 다음 변경에서 다시 어긋나는 문제를 해결하지 못했습니다.

반복된 마이그레이션 동안 세 가지 유형의 불일치가 쌓였습니다.
유형 상태
Missing Key Code에는 있으나 Sheet에는 없음
Unused Key Sheet에는 있으나 Code에서 더 이상 사용하지 않음
Duplicated Key 여러 Tab에 같은 Key가 남아 있음
01 · Design

단순 문자열 검색이 아니라, AST 순회를 선택했습니다.

번역 Key를 얼마나 정확하게 찾아내느냐가 이후 모든 검증의 신뢰도를 결정했습니다. 정규식으로 t("key") 같은 패턴을 찾는 방식은 빠르지만, 그 문자열이 실제 호출인지 주석·변수명인지 구분하지 못해 오탐을 만듭니다. 코드 구조를 그대로 읽는 AST 순회를 선택해, CallExpression만 정확히 확인하는 방식으로 문자열 검색이 만드는 오탐을 제거했습니다. 8개 프로젝트에 적용하는 동안 주석·문자열이 Key로 잘못 잡힌 사례는 보고되지 않았습니다. 다만 호출 형태만 확인하는 방식이라 동명의 다른 t() 함수까지 걸러내려면 스코프·임포트 해석이 필요하고, 그 부분은 도입하지 않았습니다.

정규식 검색이었다면

문자열 패턴만 보고 오탐을 만듭니다.

주석·일반 문자열·유사 함수명까지 t("key") 형태로 걸려, Key 목록의 신뢰도가 떨어집니다.

AST 순회를 선택

호출 구조를 직접 확인합니다.

실제 CallExpression만 순회해 값을 수집하기 때문에, 문자열 검색이 만드는 오탐을 구조적으로 막습니다.

함께 설계한 조건

정확한 추출 외에도, 유지 가능한 협업 경로를 위한 조건을 함께 뒀습니다.

Validation

불일치한 Key와 사용 위치까지 함께 처리했습니다.

Key 목록만으로는 다시 검색해야 합니다. Code Key에는 사용 File Path를 연결해 리포트의 다음 행동을 줄였습니다.

Mutation

검증과 삭제를 같은 명령으로 묶지 않았습니다.

삭제는 되돌리기 어려운 작업이므로, Validation과 분리한 GitHub Actions Workflow에서 실행하게 했습니다.

02 · Static analysis

AST 추출을 여러 단계로 나눠, 한 File의 오류가 전체 검증을 막지 않게 했습니다.

@babel/parser로 TypeScript·JSX를 Parse한 뒤 AST를 재귀 순회했습니다. t(...), i18n.t(...) 호출에서 정적으로 확인 가능한 Key만 수집해 문자열 검색이 만들 수 있는 오탐을 구조적으로 제외했습니다.

Scan boundary

필요한 Source만 Scan했습니다.

ts·tsx File을 대상으로 탐색하되 .d.ts는 제외하고, 자체 구현한 .gitignore 필터로 불필요한 Path를 걸렀습니다.

Failure isolation

Parsing 실패는 File 단위 Warning으로 남겼습니다.

한 File의 Syntax 문제 때문에 전체 결과가 사라지지 않도록 실패한 경로를 알려주고, 나머지 File의 검증은 계속 진행했습니다.

Key collection pipeline

Source에서 Key를 가져오는 경로를 작게 나눴습니다.

  1. 01 · Discoverts·tsx File 탐색
  2. 02 · Filter.d.ts·ignore 제외
  3. 03 · ParseTypeScript·JSX AST 생성
  4. 04 · Traverse대상 CallExpression 확인
  5. 05 · CollectKey와 File Path 수집
추출 대상은 i18n 호출의 구조와 인자 형태로 제한했습니다.
입력 처리 이유
t("common.save") StringLiteral의 값을 Key로 수집 정적으로 값이 확정돼 Sheet와 비교 가능
i18n.t(`common.save`) Template Literal의 첫 정적 조각을 Key로 수집 보간이 없으면 실행 시 값과 같아 Sheet와 바로 비교 가능
주석·일반 String·유사 함수명 수집하지 않음 호출 구조를 확인하지 않는 검색의 오탐을 방지
03 · Cross validation

Code와 Sheet의 Key 목록을 합치지 않고, Set Difference로 Source별 불일치를 구분했습니다.

Service Account 인증으로 Sheet의 Tab별 Key를 수집하고, Source에서 찾은 Key와 비교했습니다. Code 전용 Key와 Sheet 전용 Key는 Set 차집합으로, 중복 Key는 전역 Map으로 구분했습니다. 결과에는 Key와 Source File Path를 포함해 담당자가 다음 수정 위치를 바로 확인할 수 있게 했습니다.

유형별로 검증 결과와 후속 동작을 다르게 연결했습니다.
유형 검증 결과 후속 동작

Unused Key Sheet 전용 Key 목록을 리포트 검토 후 Cleanup 대상에 추가
Duplicated Key 전역 Map으로 중복 위치를 수집 값이 같은 중복만 정리, 값이 다르면 확인 대상으로 분리
04 · Safe maintenance

Sheet 쓰기는 자동화하되, 대량 변경에서 생길 수 있는 실패와 오삭제를 방어했습니다.

불일치를 발견하는 일과 Row를 삭제하는 일은 위험도가 다릅니다. Cleanup과 Deduplication은 GitHub Actions Workflow로 분리하고, Sheet 쓰기 과정에는 순서·요청량·재시도에 대한 안전장치를 뒀습니다.

Cleanup workflow

검토한 Key를 모든 Tab에서 정리했습니다.

검토한 삭제 목록을 기준으로 Sheet 전체 Tab에서 해당 Row를 찾아 제거하는 Flow를 만들었습니다.

Deduplication workflow

값이 같은 중복만 자동으로 정리했습니다.

전역 Map으로 동일 Key를 모은 뒤, 값이 완전히 같은 중복만 정리 대상으로 삼았습니다. 값이 다른 중복은 삭제 대신 확인이 필요한 목록으로 남겨 담당자가 검토하게 했습니다.

Google Sheets 대량 쓰기에서 고려한 실패 조건과 대응
이슈 대응 의도
앞 Row 삭제 후 뒤 Row의 Index가 바뀜 삭제할 Row를 내림차순으로 정렬 아래 Row부터 지워 Index Shift에 따른 오삭제를 피함
다수 Row를 건별 요청 batchUpdate로 묶어 요청 요청 횟수를 줄여 처리 시간과 부분 실패 지점을 줄임
429·Quota 초과 1초 → 2초 → 4초, 최대 3회 지수 Backoff 일시적 실패로 정리 전체가 중단되는 일을 줄임
05 · Trade-off

정적 분석이 확인할 수 없는 경계와, 남겨둔 후속 과제를 함께 정리했습니다.

모든 검증을 자동화하지는 못했습니다. 값이 정적으로 확정되지 않는 경우는 검증 대상에서 제외했고, 성능·품질을 더 다듬을 여지도 후속 과제로 남겨뒀습니다.

정적 분석의 한계와 후속 과제를 구분했습니다.
유형 항목 내용
제외 대상 Dynamic Key 변수로 전달하는 Key는 값을 정적으로 확정할 수 없어 검증 대상에서 제외
제외 대상 동명 함수 t라는 이름과 호출 형태만 보고 판정하므로, i18n이 아닌 동명 함수의 호출도 수집될 수 있음. 스코프·임포트 해석은 도입하지 않음
후속 과제 Template Literal 인식 보간이 포함된 Template Literal Key는 앞부분 정적 문자열만으로 인식돼 완전한 Key로 확정되지 않는 경우가 있어, 인식 정밀도를 높이는 개선 필요
후속 과제 Worker·Cache 대형 Codebase의 처리 시간을 줄이기 위한 도입 필요
후속 과제 Unit Test AST 추출 로직에 대한 작성 필요
06 · Results

프로젝트별 스크립트가 아니라, 재사용 가능한 공용 도구로 배포했습니다.

Commander 기반 i18n-checker run <project> <sheetId> <gcpKey> 명령으로 실행 경로를 통일했습니다. 먼저 백오피스 프로젝트에 적용해 검증하고, 프론트·기획·디자인 팀에 직접 소개한 뒤 GitHub Packages로 배포했습니다. 각 프로젝트는 같은 CLI를 로컬 또는 CI에 연결하고, Sheet 정리는 별도의 Workflow Button으로 실행할 수 있게 역할을 나눴습니다.
