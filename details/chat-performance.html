CASE 02 · NEPTO · Chat performance

하나의 느림에
숨겨진 두 가지 원인을 찾았습니다.

같은 화면에서 발생했지만 원인은 달랐습니다. 메시지 목록은 메시지가 쌓일수록 Query·State Update·Rendering 비용이 함께 커졌고, 채팅방 입장은 메시지 수와 무관하게 매번 같은 Member·Read State Sync를 반복했습니다. 비용이 커지는 축이 다르면 해법도 달라야 한다고 판단해 두 Pipeline을 나눠 측정하고, Data Range와 Execution Timing을 각각 다시 설계했습니다. E2E 암호화·배치 큐 인프라는 기존 구현을 그대로 사용했습니다. 이 문서는 포트폴리오의 결과 요약보다 측정과 설계 판단, 그리고 남겨 둔 부채를 자세히 기록한 문서입니다.

Starting point

“채팅이 느리다”는 하나의 증상 아래, 서로 다른 두 원인이 있었습니다.

대용량 DM에서 화면이 멈추거나 앱이 종료되는 현상, 그리고 방에 들어갈 때 목록이 늦게 그려지는 현상은 사용자 입장에서 모두 “채팅이 느리다”로 느껴집니다. 메시지 렌더링 이슈는 방에 쌓인 메시지 수에 비례해 나빠졌고, 입장 문제는 메시지 수와 상관없이 동기화 과정의 반복으로 인해 발생했습니다.

따라서 두 Pipeline을 먼저 분리해 정의한 뒤 각각 측정 기준을 세웠습니다. 메시지 렌더링은 “한 번의 Load에서 무엇을 얼마나 읽고 얼마나 갱신하는가”, 입장은 “방에 들어가는 순간 반드시 실행되어야 하는 것이 무엇인가”를 질문으로 잡았습니다.

같은 화면에서 관측되지만, 두 Pipeline은 원인과 비용이 커지는 축이 서로 다릅니다.
Pipeline 사용자에게 보이는 증상 원인 요약
Message list 스크롤 중 화면 멈춤 · 앱 종료 방의 전체 Message를 먼저 읽어 정렬한 뒤 일부만 잘라 Rendering. 한 번의 Load에서 Cursor·다음 Data 존재 여부·목록 길이·Message 배열이 연쇄적으로 갱신됨 메시지 수에 비례 보여줄 양이 아니라 가진 양만큼 읽음
Room entry 방에 들어가도 메시지 목록이 늦게 그려짐 입장할 때마다 탈퇴 멤버 조회와 멤버별 마지막 읽은 Cursor 조회를 비동기로 실행하고, 그 결과를 모두 기다린 뒤에야 Read Count를 갱신하고 메시지를 Load 입장마다 비동기 조회·갱신 반복 메시지 수와 무관하게 매번 실행됨
01 · Message list — AS-IS

전체를 읽고 잘라 쓰는 구조에서는, 20개를 보여주기 위해 전부를 읽고 있었습니다.

기존 목록은 DB ⇒ state ⇒ Rendering 구조였습니다. 방의 Message를 모두 조회해 생성 순으로 정렬한 뒤, 최초 Rendering 개수만큼 잘라 State에 담았습니다. 이후 과거·최신·특정 메시지로 이동하는 동작은 하나의 Load 함수 안에서 상태 값을 보고 분기하는 방식으로 처리했습니다.

날짜 구분선, 프로필 노출 여부, 시간 표시 여부처럼 앞뒤 메시지와의 관계로 정해지는 메시지 부가 정보 역시 목록을 그릴 때마다 전체를 다시 계산했고, 이 계산 비용도 메시지 수에 비례해 커졌습니다.

Cost 01 · Read amount

보여줄 양이 아니라 가진 양만큼 읽습니다.

화면에 필요한 것은 20개인데 조회 대상은 방 전체 Message입니다. 정렬까지 전체 집합에 걸리므로, 대화가 길어질수록 첫 Rendering에 도달하는 비용이 같이 늘어납니다.

Cost 02 · Update fan-out

한 번의 Load가 여러 State를 연쇄로 흔듭니다.

Cursor, 다음 Data 존재 여부, 목록 길이, Message 배열이 하나의 Load 안에서 함께 갱신됩니다. 갱신 지점이 흩어져 있으면 어떤 값이 어떤 Re-render를 유발했는지 추적하기 어렵고, 그만큼 줄일 대상도 특정하기 어렵습니다.

Cost 03 · Derived recompute

메시지 하나가 바뀌어도 목록 전체를 다시 계산합니다.

날짜 구분선, 아바타 노출 여부 같은 부가 정보는 앞뒤 메시지와의 관계로 정해지는데, 이 관계를 매번 목록 전체를 훑어 다시 계산했습니다. 메시지가 추가되거나 바뀔 때마다 이 비용도 메시지 수에 비례해 커졌습니다.

측정에 앞서 세운 가설

읽는 양, 갱신하는 State, 파생 속성 재계산을 함께 줄여야 하며, 하나만 줄이면 체감이 크게 달라지지 않는다고 봤습니다. 읽는 양만 줄이면 갱신 연쇄와 재계산 비용이 남고, 갱신만 줄이면 첫 조회 비용과 재계산 비용이 그대로 남기 때문입니다.

02 · Message list — TO-BE

사용자 행동 네 가지를 각각 독립된 Range Query로 분리했습니다.

구조를 DB ⇒ store ⇒ Rendering으로 바꿨습니다. 핵심은 두 가지입니다. 첫째, 한 번에 모두 읽고 잘라 쓰는 대신 그때그때 필요한 범위만 DB에서 읽습니다. 둘째, 분기 하나에 몰려 있던 로직을 Action별 함수로 분리해 각 Action이 무엇을 읽고 어떻게 병합하는지 함수 단위로 드러나게 했습니다.

Design 01 · Query unit

조회의 단위를 “목록”이 아니라 “사용자 행동”으로 잡았습니다.

기존에는 하나의 Load 함수가 상태 값을 보고 무엇을 할지 결정했습니다. 바꾼 구조에서는 처음 들어오기, 위로 올라가기, 아래로 내려오기, 특정 메시지로 점프하기가 각각 독립된 조회 단위입니다. 조회 방향과 정렬, 기준 Cursor가 행동마다 다르므로 하나로 묶을 이유가 없다고 봤습니다.

Design 02 · Bidirectional

점프 동작만 조회를 두 번 수행합니다.

특정 메시지로 점프하는 동작은 기준점의 위·아래가 모두 비어 있습니다. 한 방향만 채우면 사용자가 곧바로 반대 방향으로 스크롤했을 때 빈 화면을 만나므로, 기준 메시지를 가운데 두고 이전 방향과 이후 방향을 각각 조회해 양쪽을 함께 채웁니다.

Action별 조회 기준과 Store 병합 방식. Store는 최신 메시지가 앞에 오도록 유지하므로, 과거 방향은 뒤에서 최신 방향은 앞에서 병합됩니다.
Action 사용자 행동 조회 기준 Store 병합
initial 채팅방에 처음 들어옴 최신 메시지부터 20개 Store를 새로 채움
oldest 위로 스크롤해 이전 대화를 봄 현재 Cursor 기준 과거 방향, 내림차순 기존 목록 뒤에 이어 붙임
latest 아래로 스크롤해 최신으로 돌아옴 현재 Cursor 기준 최신 방향, 역방향 정렬 기존 목록 앞에 붙임
target 안 읽은 메시지·인용 메시지로 점프 기준 메시지의 이전·이후를 각각 조회 이후 방향 · 기준 메시지 · 이전 방향 순으로 재구성
03 · Derived attributes

부가 정보는 앞뒤 메시지에 따라 달라지므로 바뀐 지점 주변만 다시 계산했습니다.

날짜 구분선, 프로필 노출 여부, 시간 표시 여부, 내 메시지 여부는 메시지 하나만 봐서는 결정할 수 없습니다. 같은 사람이 연속으로 말하면 아바타를 숨기고 날짜가 바뀌면 구분선을 넣는 것처럼, 앞뒤 메시지와의 관계로 정해지는 파생 상태이기 때문입니다.

그래서 메시지가 하나 삽입될 때마다 목록 전체를 다시 계산하면 메시지 수에 비례하는 비용이 됩니다. 하지만 실제로 관계가 깨지는 지점은 삽입된 위치의 바로 앞뒤뿐입니다. 갱신 범위를 그 지점으로 한정해 반복 계산을 상수 범위로 고정했습니다.

04 · Re-render policy

“무엇을 비교 대상에 넣을지”가 곧 Re-render 정책이라고 봤습니다.

Message Item에 Custom Memo Comparator를 적용하면서, 비교 대상을 편의로 고르지 않고 화면에 실제로 영향을 주는 값이라는 기준을 먼저 세웠습니다. 비교 대상이 넓으면 불필요한 Re-render가 남고, 좁으면 바뀐 내용이 화면에 반영되지 않는 결함이 생기기 때문입니다.

Include / Content

본문과 전송 상태

메시지 본문과 전송 상태는 그대로 화면에 나타납니다. 전송 중에서 전송됨으로 바뀌는 순간이 사용자에게 보여야 하므로 반드시 비교 대상입니다.

Include / Derived

메시지 부가 정보

날짜표시선·시간표시 등 앞 절에서 소규모로 갱신한 값들입니다. 소규모 갱신으로 값이 바뀐 항목만 정확히 다시 그리게 하려면 이 값들이 비교 대상에 포함돼야 합니다.

Include / Read state

메시지 읽음 수

메시지 읽음 수는 다른 멤버의 읽음 확인 소켓 이벤트로 갱신되고, 이 이벤트는 기존 배치 큐를 거쳐 묶여 들어옵니다. 가장 자주 바뀌는 값이지만 빼면 읽음 표시가 갱신되지 않으므로 비교 대상에 포함하고, 큐가 묶어준 단위로 Store를 한 번에 갱신해 Re-render가 이벤트 건수가 아니라 배치 단위로 발생하게 했습니다.

05 · Scroll state

스크롤 프레임과 UI State Update를 분리했습니다.

스크롤 Offset은 프레임마다 바뀝니다. 이 값을 그대로 Store에 반영하면 스크롤하는 내내 Subscriber가 깨어납니다. 그래서 Offset 자체는 Store 안에 보관하되 Subscriber를 깨우지 않는 방식으로 대입하고, 최신 메시지 이동 버튼의 노출 여부나 Bottom 도달 여부처럼 실제로 UI가 바뀌는 값만 갱신했습니다.

06 · Scroll anchor

과거 메시지를 불러올 때 사용자의 스크롤 위치가 밀리던 문제를 수정했습니다.

위로 스크롤해 과거 메시지를 불러오면 목록 위쪽에 항목이 추가되면서 보고 있던 화면이 밀립니다. Embed·인용·이미지처럼 나중에 높이가 확정되는 메시지가 섞이면 더 심해집니다. 이 문제를 화면마다 따로 대응하지 않고, 위로는 과거를 아래로는 최신을 모두 이어 붙이는 공통 리스트 컴포넌트가 스크롤 유지 옵션을 소유 하도록 만들었습니다.

목록 구현체는 한 번 되돌리는 과정을 거쳤습니다. 처음에는 View를 재활용하는 FlashList를 썼습니다. 메시지가 수만 개여도 실제로 Viewport에 보이는 것은 평균 6~10개이므로, 이미 만들어진 메시지 컴포넌트를 재활용하는 편이 유리하다고 판단했기 때문입니다.

다만 FlashList는 아직 그리지 않은 항목의 높이를 추정값으로 미리 받아야 합니다. 사진이 들어간 메시지와 텍스트만 있는 메시지는 높이 차이가 커서 이 값이 자주 어긋났고, 어긋난 만큼 스크롤 위치가 튀었습니다. 사진 크기를 줄이고 추정값을 중앙값에 맞춰 완화해봤지만 근본적으로 해결되지는 않았습니다. 채팅은 위로 스크롤할 때마다 목록 위쪽에 항목이 붙는 구조여서, 재활용으로 아끼는 비용보다 스크롤 위치가 밀리는 손해가 더 컸습니다. 그래서 스크롤 유지 옵션을 직접 다룰 수 있는 TwoWayFlatList로 되돌렸습니다.

Option 속성을 컴포넌트 내부로 옮기고, Props에서 제거

스크롤 유지 옵션을 공통 컴포넌트 내부로 넣고 외부에 노출되는 Props 타입에서는 제거했습니다. 사용하는 쪽에서 값을 다르게 넣어 동작이 깨지는 경우를 런타임이 아니라 컴파일 타임에 막기 위해서입니다. 로딩 인디케이터도 Header·Footer로 흡수해 화면마다 다르게 구현되지 않도록 했습니다.

자동 스크롤은 세 조건이 모두 true일 때만

새 메시지가 왔을 때 항상 아래로 내리면 과거 대화를 읽던 사용자의 화면이 강제로 이동합니다. 그래서 최신 페이지 · 다음 Data 없음 · 현재 Bottom 세 조건이 모두 true일 때만 자동 스크롤을 허용했습니다. 하나라도 false면 위치를 유지하고, 대신 최신 메시지 이동 버튼으로 알립니다.

07 · Read count model

서버가 내려주지 않는 값을, 멤버별 Cursor에서 파생시켰습니다.

그룹 DM의 “N명이 읽음”은 서버가 메시지마다 숫자를 내려주지 않습니다. 서버가 가진 것은 멤버별 마지막으로 읽은 메시지 ID라는 Cursor뿐입니다. 그래서 Client가 Cursor와 메시지 ID를 비교해 카운트를 계산합니다. 메시지 ID가 Cursor 이하이면 그 멤버는 해당 메시지를 읽은 것으로 판정합니다.

화면에 보이는 값은 카운트 그 자체가 아니라 두 단계 규칙으로 정해집니다. 모두 읽은 메시지는 아무것도 표시하지 않고, 그렇지 않으면 방의 멤버 수에서 읽은 횟수를 뺀 값, 즉 아직 읽지 않은 사람 수를 보여줍니다.

이 read_count는 04의 Re-render 비교 대상에도 포함되고 08의 방 입장 흐름에서도 다시 갱신되는, 두 Pipeline이 함께 쓰는 값입니다. 그래서 이 절에서는 계산 비용을 줄이는 것과 별개로, 멤버가 바뀔 때도 값이 어긋나지 않도록 정합성을 맞추는 부분까지 함께 다룹니다.

07-1 · Avoiding recomputation

이미 확정된 값은 다시 계산하지 않도록, 완료 표시와 초기값 결정을 함께 적용했습니다.

읽음 계산은 멤버 Cursor × 메시지의 이중 순회라 방 인원이 늘고 대화가 길어질수록 순회 대상이 곱으로 커집니다. 이미 값이 정해진 지점을 다시 순회하지 않도록 두 곳에서 손을 댔습니다.

먼저 카운트가 방 멤버 수에 도달한 메시지에 완료 표시를 남기고 이후 계산 대상에서 제외했습니다. 오래된 메시지 대부분은 이미 전원이 읽은 상태라, 순회 대상이 “방의 전체 메시지”에서 “아직 전원이 읽지 않은 최근 메시지”로 줄어듭니다.

또한 메시지를 받은 뒤 화면에 들어가서 다시 계산하면 같은 값을 두 번 구하는 중복 계산이 생깁니다. 대신 메시지를 파싱하는 시점에 이미 알고 있는 사실을 초기값으로 넣어 이 중복을 없앴습니다. 본문 메시지는 발신자가 반드시 읽은 상태이고, 내가 그 방을 보고 있었다면 나도 읽은 상태이기 때문입니다.

07-2 · Membership change

멤버가 드나들면 “읽음”의 의미 자체가 달라집니다.

읽음 카운트는 방의 멤버 수를 기준으로 완료를 판정합니다. 초대나 나가기로 멤버 수가 바뀌면 이미 계산해 둔 값과 완료 표시가 전부 어긋납니다. 두 경우를 같은 규칙으로 처리하지 않고, 각각의 의미에 맞게 보정 방향을 나눴습니다.

멤버 변동 시 Read Count 재정합 규칙
이벤트 기준점 보정 함께 처리한 것
유저 초대 초대된 유저는 초대 직전에 발송된 메시지를 항상 마지막으로 읽은 메시지로 받습니다 그 메시지를 기점으로 이전 메시지의 카운트를 모두 +1 초대 이전 메시지는 초대된 유저에게 노출되지 않으므로 읽음으로 확정됩니다. 카운트와 멤버 수가 함께 늘어 이미 완료 표시된 메시지는 그대로 유지되고 재계산 대상에 들어오지 않습니다

나가기 메시지의 Cursor를 갱신하지 않는 이유

나가기 메시지 시점까지 읽었다고 기록하면, 방을 떠난 사람이 마지막 메시지를 읽은 것으로 남습니다. 이 상태에서 인원까지 줄이면 카운트가 한 번 더 어긋나므로, Cursor는 그대로 두고 인원 기준만 보정하도록 방향을 통일했습니다.

08 · Room entry

방에 들어가는 순간 반드시 해야 하는 일만 남겼습니다.

기존 입장 흐름은 네 단계였습니다. 키 교환 메시지 전송과 알림 카운트 감소, 탈퇴 멤버 조회, 멤버별 마지막 읽은 Cursor 조회를 비동기로 실행한 뒤, 이 비동기 작업이 모두 끝나야 Read Count를 갱신하고 메시지를 Load했습니다.

문제는 2·3번 과정이 필요 여부와 상관없이 입장할 때마다 반복된다는 점이었습니다. 실제로 이 로직이 동작하는 경우 UI가 그려지기까지 예상보다 시간이 많이 걸렸습니다.

이 절의 측정값은 입장 시 실행되던 동기화 로직의 실행 시간이며, 목록이 실제로 그려지는 비용은 02–06절의 렌더링 개선에서 따로 다뤘습니다.

08-1 · Timing shift

없앤 것이 아니라, 실행 시점을 옮겼습니다.

탈퇴 멤버 조회와 Cursor 조회는 여전히 필요한 작업입니다. 다만 그것이 방에 들어가는 순간에 실행될 이유는 없었습니다. 그래서 두 작업을 앱을 처음 켤 때(Splash Screen)와 백그라운드에서 포그라운드로 돌아올 때로 옮겼습니다.

추가로 소켓으로 메시지를 수신할 때마다 메시지들 중 각 유저별 마지막 메시지 ID를 Cursor로 갱신해 두었습니다. 그 결과 방에 들어가는 시점에는 이미 DB에 반영된 현재 상태를 그대로 읽어 쓰기만 하면 됐습니다.

  1. App launchSplash Screen에서 공통 Sync 1회
  2. Foreground백그라운드 복귀 시 공통 Sync 1회
  3. Socket메시지 수신마다 유저별 Cursor 갱신
  4. Room entry저장된 현재 상태를 그대로 사용
