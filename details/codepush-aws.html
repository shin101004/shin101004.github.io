CASE 03 · NEPTO · Update experience

Beta에서 확인한 Update 피로,
출시 전 OTA로 해결했습니다.

Beta 기간에는 UI와 기능을 보완할 때마다 새로운 TestFlight Build를 배포하고, Tester가 그 Build를 다시 설치해야 했습니다. 최신 Build가 설치되지 않아 서로 다른 Version을 사용하는 상황을 보며, 이 마찰이 정식 사용자에게도 이어질 수 있다고 판단했습니다. 이 문제의식에 프론트팀과 CTO 모두 공감해 OTA 도입을 진행하기로 했고, 저는 이 작업을 먼저 제안해 맡았습니다. Native 변경이 없는 JavaScript·Asset Update를 더 짧은 경로로 전달하되, App Center 종료 이후에도 지속할 수 있도록 AWS 기반 Self-hosted CodePush를 구현하고 기존 EKS 환경에 연동했습니다.

  • Client contract SDK · CLI API 유지 기존 Update Flow를 바꾸지 않음
  • Storage consistency Multi-item DynamoDB Stateless · TransactWriteItems
  • Package delivery S3 직접 다운로드 API는 메타데이터만 응답
  • Runtime 기존 EKS 연동 공통 클러스터는 새로 구축하지 않음
Starting point

Beta에서 보인 Update 피로를, 출시 후의 사용자 경험 문제로 해석했습니다.

Beta에서는 개선 내용을 확인하려면 새 Build를 배포하고 설치해야 했습니다. 이 과정은 변경의 크기와 무관하게 반복됐고, 최신 Build가 설치되지 않은 Tester가 생기면서 같은 기능을 서로 다른 상태에서 확인하게 됐습니다. 단순히 Beta 운영의 편의성 문제가 아니라, 출시 후 작은 수정이 사용자에게 도달하는 속도에 영향을 줄 수 있는 문제로 봤습니다.

01 · Decision

Expo OTA vs Self-hosted CodePush, 종료 일정 안에서 실현 가능한 쪽을 택했습니다.

Expo OTA(EAS Update)를 붙이려면 기존 RN Community CLI 기반 프로젝트에 구독 비용과 별개로 Expo 계정·EAS 종속성까지 새로 들여야 했습니다. 이미 아키텍처가 잡혀 있던 프로젝트에는 이 종속성 자체가 부담이었고, Self-hosted CodePush는 App Center 수준의 설정만으로 붙일 수 있어 진입장벽이 낮았습니다. 이 판단 근거를 프론트 리드와 CTO에게 공유하고 컨펌받았습니다.

Alternative

Expo OTA(EAS Update) 도입

구독 비용뿐 아니라 Expo 계정·EAS 종속성까지 필요해 이미 구조가 잡힌 프로젝트에는 진입장벽이 높았습니다.

Selected

Self-hosted CodePush

기존 Client SDK·CLI 호환성과 AWS·EKS Runtime 적합성을 우선해 선택했습니다. 대신 운영 요소는 직접 구성해야 했습니다.

선택의 기준은 “새 기능”이 아니라 “지속 가능한 경로”였습니다.

App Center 종료 일정이 있었기 때문에 당장 빠르게 도입할 수 있는 도구보다, 출시 후에도 유지할 수 있는 구조가 필요했습니다. Self-hosted 방식은 운영 책임이 늘지만 기존 Client 계약을 보존하면서 사내 Runtime을 활용할 수 있다는 점을 더 크게 봤습니다.

02 · Compatibility boundary

Route를 다시 만들지 않고, Storage Implementation만 AWS로 교체했습니다.

CodePush 서버는 Management API와 Acquisition API로 CLI·React Native Client의 요청을 받고, 내부적으로는 이미 Storage Interface를 통해 저장소에 접근하고 있었습니다. 약 30개 메서드로 구성된 이 계약을 유지한 채 S3Storage를 구현해, 외부 Flow를 바꾸지 않고 내부의 Azure 의존성만 교체했습니다.

유지한 API 계약과 새로 구현한 부분
영역 유지한 것 교체·정리한 것
Client Update Flow React Native Client의 Update Check와 Package 수신 방식 응답에 포함되는 Package URL이 Azure 경로가 아닌 S3 URL을 가리키도록 변경
Release Management CLI가 사용하는 앱·배포·Package 관리 API 업로드 호출을 S3Storage에 연결하고 Package 파일을 S3에 저장
Server Storage Storage Interface와 상태 모델 Azure 의존성을 제거하고 엔티티별 DynamoDB Item·ConditionExpression·TransactWriteItems 기반 AWS 접근 계층 추가
03 · Storage design

큰 Package와 동시 변경되는 상태 정보를, 책임과 정합성에 맞게 나눴습니다.

릴리스 ZIP과 diff 파일은 클라이언트가 직접 받는 큰 바이너리이고, 앱·계정·배포·Access Key·Package History는 작은 구조화된 상태입니다. 두 종류를 한 저장소에 넣지 않고 Package는 S3, 서비스 상태는 DynamoDB로 분리했습니다. DynamoDB 안에서도 전체 상태를 하나의 Snapshot으로 덮어쓰지 않고 엔티티별 Item으로 나눠, 각 요청이 필요한 상태만 읽고 변경하도록 구성했습니다.

Storage 01 · S3

Package를 의미 있는 Key로 관리했습니다.

배포 채널과 앱 Version, Blob ID를 조합한 Key로 릴리스 Package를 저장해 어떤 Deployment의 어떤 Version인지 Object 경로에서 확인할 수 있게 했습니다. getBlobUrl은 항상 동일한 규칙으로 계산되는 S3 URL을 반환하도록 단순화했습니다.

Storage 02 · DynamoDB

메타데이터를 엔티티별 Item으로 나눴습니다.

전체 상태를 단일 Item과 프로세스 메모리 Snapshot으로 관리할 때 전체 데이터가 단일 Item의 400KB 한도에 묶이고 Pod별 상태가 달라지는 문제를 피하기 위해 Account·App·Deployment·Package를 별도 Item으로 저장했습니다. 각 Storage 메서드는 요청 처리에 필요한 Item만 읽고, 릴리스는 새 Package 생성·직전 Package Rollout 해제·Deployment META의 latestSeq·currentLabel· version 갱신을 ConditionExpression이 포함된 TransactWriteItems로 원자적으로 반영합니다.

04 · Release & update flow

등록은 DynamoDB Transaction으로 확정하고, 다운로드는 S3로 바로 보냈습니다.

릴리스 시에는 CLI가 Management API를 통해 Package와 메타데이터를 등록합니다. API는 S3 업로드와 DynamoDB Transaction의 완료를 기다린 뒤에만 성공을 반환하고, 앱 실행 시에는 Acquisition API가 앱 Version과 배포 정보를 비교해 받을 Package의 S3 URL을 응답합니다. 이때 실제 ZIP 다운로드는 API 서버를 거치지 않습니다. 저장 실패를 성공으로 보고하지 않으면서 API의 바이너리 전달 부담도 없앴습니다.

Management path

CLI Release → 저장소 반영

  1. Step 1CLI가 릴리스 정보를 Management API에 등록
  2. Step 2ZIP Package의 S3 업로드 완료를 확인
  3. Step 3새 Package·직전 Rollout·Deployment META를 Transaction으로 반영
  4. Step 4두 저장소가 성공한 뒤 API가 성공 응답
Acquisition path

App Update Check → S3 수신

  1. Step 1앱이 현재 Version으로 Update Check 요청
  2. Step 2API가 필요한 DynamoDB Item을 조회해 Package를 선택
  3. Step 3앱이 응답된 S3 URL에서 ZIP을 직접 다운로드
두 Flow를 분리했을 때 각 구성 요소가 맡는 일
구성 요소 릴리스 시 업데이트 확인 시
CodePush API CLI 요청을 검증하고 S3·DynamoDB 완료 후 성공을 반환 현재 앱 Version과 Deployment를 확인해 적용할 Package URL 응답
S3Storage ZIP Package 업로드를 기다리고 실패를 API까지 전달 정적 S3 URL을 계산해 API 응답에 사용
Amazon S3 릴리스 번들을 보관 React Native 앱에 Package 파일을 직접 전달
Amazon DynamoDB ConditionExpression을 포함한 TransactWriteItems로 새 Package·직전 Rollout·Deployment META를 함께 반영 배포 식별과 Package History에 필요한 Item을 조회
05 · Runtime & operations

관리형 서비스가 맡던 운영 요소를, 기존 EKS 환경의 배포 구성으로 옮겼습니다.

서버는 node:20-alpine 기반 이미지로 컨테이너화하고, 기존 EKS 환경에 배포·연동했습니다. ALB Ingress, liveness·readiness probe, Kubernetes Secret 주입과 Kustomize 기반 이미지 태그 치환을 구성했으며, GitHub Actions로 빌드와 배포를 연결했습니다.

Authentication

Azure AD 경로를 걷어내고 접근 제어를 정리했습니다.

Azure AD OIDC와 passport-azure-ad 의존성을 제거하고, GitHub OAuth와 Bearer Token(AccessKey) 기반 접근 제어를 사용했습니다. OAuth Client Secret은 코드나 이미지가 아니라 Kubernetes Secret으로 주입했습니다.

Deployment scope

배포된 환경에서 End-to-end Flow를 확인했습니다.

릴리스 등록부터 앱의 Update Check, S3 Package 다운로드까지 실제 흐름을 확인했습니다.

06 · Completion

Storage를 바꾼 뒤, CLI와 앱이 기존과 동일하게 동작하도록 나머지를 맞췄습니다.

Storage를 바꾸는 것만으로는 기존 관리 Flow가 완성되지 않았습니다. 앱을 생성할 때 Owner Collaborator를 등록하고, 현재 요청 계정을 표시하며, 외부 Package URL과 업로드 호출부를 새 Storage Flow에 맞췄습니다. 프로세스 메모리 복원에 의존하지 않는 요청 단위 조회와 저장 오류 전파, 권한 처리처럼 전환 뒤에야 보이는 경계도 함께 정리했습니다.

저장소 전환 후 함께 정리한 호환성 경계
경계 보완한 내용 유지하려는 사용자·관리 경험
App 권한 앱 생성 계정을 Owner 권한의 Collaborator로 등록하고 현재 요청 계정 정보를 보완 기존 관리 API에서 앱 소유권과 협업자 권한을 확인하는 흐름
Package URL 환경변수와 S3 Object Key를 조합해 외부에서 받을 URL을 생성 Client가 기존 Update Check 응답만으로 Package를 수신하는 흐름
상태 영속화 엔티티별 Item을 요청 단위로 읽고 쓰며, 저장 완료를 기다려 오류를 호출 경로까지 전달 Pod·재시작 여부와 무관하게 DynamoDB의 같은 상태를 사용하는 서버 동작
Runtime 의존성 Azure Storage·Key Vault·Identity SDK와 Azure AD 경로 제거 AWS 기반 환경에서 단일한 설정·인증 경로로 서버를 실행하는 구조
07 · Results

Self-hosted CodePush를 통해 OTA 경험을 제공할 수 있었습니다.

기존 SDK·CLI API는 그대로 유지해 Client 쪽 변경 없이 전환을 마쳤고, Native 변경이 없는 JavaScript·Asset 수정은 스토어 심사와 새 Build 설치를 기다리지 않고 배포할 수 있게 됐습니다. 스토어 심사가 필요한 Native 변경은 이 경로의 범위에 포함되지 않습니다.
