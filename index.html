CASE 01

잘못된 UX 설계,
14가지 개선안을 제시했습니다.

사용자의 Core Action을 방해하는 잘못된 UI/UX를 발견했습니다. 대형 서비스와 비교하며 근거를 만들고, 일부 화면에서 방향을 먼저 반영한 뒤 제안·명세·개발로 연결했습니다.

VERSUS · 2025—2026
평균 9% → 16% 일간 평균 Core Action 전환 수
12 / 14 UX 개선안 채택 · 14개 제안
  1. Problem

    Core Action을 방해하는 UI/UX

    Beta 출시 전후의 화면은 같은 정보가 여러 위치에 반복될 뿐만 아니라, 불필요한 정보가 너무 크게 강조되고 있었습니다. 사용자가 서비스 내에서 제공받아야 할 Core Action까지는 여러 단계를 거쳐야 한다는 점을 문제로 인지하게 되었습니다.

  2. Evidence

    대형 서비스 UX 패턴 비교

    사용자가 필요한 정보를 수집하고, 서비스 이동을 거쳐 Core Action까지 도달하는 과정을 Versus와 대형 서비스에서 Feature 단위로 나눠 비교했습니다. 각 단계에서 나타나는 정보 구조와 이동 방식의 차이를 정리했습니다.

  3. Decision

    시각적 비교로 개선 필요성을 설득

    문서만으로 설명하는 대신 일부 화면에 개선 방향을 먼저 적용해 Before·After 시안을 만들었습니다. 기존 화면의 문제와 변화 방향을 한눈에 비교할 수 있게 제시해 개선 필요성에 대한 팀의 동의를 이끌어냈습니다.

  4. Execution

    12개 개선안의 프로덕트 반영

    공통 Navigation·프로필·거래 과정을 포함한 14가지 개선안을 제시했고, 이 가운데 12개가 채택됐습니다. 채택된 개선안은 상세 Data와 Edge Case, 사용자 시나리오까지 명세화해 직접 구현했습니다.

CASE 02

하나의 느림에
숨겨진 두 가지 원인을 찾았습니다.

같은 채팅 화면에서 발생했지만 원인은 달랐습니다. 메시지가 쌓일수록 Query·State Update·Rendering 비용이 커졌고, Room Entry에서는 Member·읽음 수 Sync가 반복됐습니다. 두 Pipeline을 나눠 측정하고 Data Range와 Execution Timing을 각각 다시 설계했습니다.

NEPTO · 2023—2025
10–20ms Message Rendering · 기존 약 300–400ms
0.69ms 신규 메시지 Room Entry · 기존 300.08ms
O(n) → O(1) 부가 정보 계산 · Full List → Insertion Point
  1. Problem

    같은 느림처럼 보였지만 원인이 다른 두 병목

    대용량 DM에서는 Full Message List를 읽은 뒤 일부만 Rendering하는 비용으로 화면이 멈추거나 앱이 종료됐습니다. 반면 채팅방 입장 지연은 방마다 공통 Member·읽음 수 Sync를 다시 실행하는 구조에서 발생했습니다.

  2. Profiling

    Query·Rendering과 Room Entry 비용을 분리

    DB Query, UI State Update, List Rendering, Member·읽음 수 계산의 실행 시간을 나눠 측정했습니다. Message 수에 따라 커지는 Rendering 비용과 입장할 때마다 반복되는 공통 Sync가 별개의 병목임을 확인했습니다.

  3. Rendering

    필요한 Message Range만 조회하고 다시 계산

    Initial Load는 최신 20개, Previous·Latest 이동은 현재 Cursor를 기준으로 필요한 Range만 Query하도록 분리했습니다. 각 Query Result는 Store에 Merge하고 UI는 이 Store만 Subscribe하도록 State Update Path를 단일화했습니다. Date Chip·Avatar·Timestamp처럼 이웃 Message에 의존하는 부가 정보는 전체 List가 아닌 Insertion Point 주변 최대 3개와 Page가 맞닿는 Boundary 2개만 재연산해 O(n) 비용을 O(1)로 제한했습니다.

  4. Room Entry

    공통 Sync를 App Lifecycle로 이동

    채팅방에 입장할 때마다 실행되던 Member·읽음 수 Sync를 App Launch·Foreground Transition·Socket Event 시점으로 옮겼습니다. Room Entry에서는 RealmDB에 반영된 현재 State로 Message Load를 바로 이어가도록 구현했습니다.

  • React Native
  • TypeScript
  • Realm DB
  • Zustand
  • Socket
  • TwoWayFlatList
CASE 03

Beta에서 확인한 Update 피로,
출시 전 OTA로 해결했습니다.

TestFlight 운영에서 확인한 Update 마찰이 실제 사용자에게 이어지지 않도록 OTA 도입을 추진했습니다.
App Center 종료에 대응해 AWS 기반 Self-hosted CodePush를 구축했습니다.

NEPTO · 2024
  1. Problem

    TestFlight 배포에서 생긴 Update 마찰과 Version Gap

    Beta 기간에는 UI 수정과 기능 보완이 잦았습니다. OTA 도입 전에는 변경된 내용을 확인하기 위해 새로운 TestFlight Build를 배포해야 했고, Tester 기기에도 해당 Build가 새로 설치되어야 했습니다. 일부 Tester에게 최신 Build가 설치되지 않아 서로 다른 Build로 앱을 사용하는 상황을 확인했습니다.

  2. Evidence

    최신 개선을 바로 전달하는 OTA 필요성 확인

    이 경험을 통해 정식 출시 후에도 개선 사항이 사용자에게 늦게 전달되는 문제가 반복될 수 있다고 판단했습니다. Native 변경이 없는 JavaScript·Asset Update를 별도의 App Build 설치 없이 전달할 수 있도록, 출시 전에 OTA 배포 기반을 마련하고자 했습니다.

  3. Decision

    출시 이후까지 지속 가능한 Self-hosted OTA 설계

    App Center 종료가 출시 약 1년 뒤로 예정되어 있어, 이 문제를 먼저 제안해 맡았습니다. EAS는 구독 비용에 더해 Expo 계정·EAS 종속성까지 새로 들여야 했던 반면, Self-hosted CodePush는 기존 Client SDK·CLI 호환성과 사내 AWS·EKS Runtime을 그대로 활용할 수 있었습니다. 이 판단 근거를 프론트 리드·CTO와 공유해 Self-hosted 방식을 우선 진행하기로 했습니다.

  4. Execution

    출시 환경에서 사용할 Self-hosted OTA Flow 완성

    기존 Storage Interface와 API를 유지한 채 Azure Storage를 S3·DynamoDB로 교체했습니다. 기존 사내 EKS Runtime을 재사용하는 방향으로 CTO와 협의해 변경한 Server를 배포하고, CLI Release Registration부터 Client Update Check와 S3 Bundle Download까지 실제 OTA Flow를 확인했습니다.

  • Node.js
  • TypeScript
  • Express
  • AWS SDK v3
  • S3
  • DynamoDB
  • Kubernetes
  • Amazon EKS

  1. Problem

    동기화되지 않는 코드와 번역 시트

  2. Evidence

    Source Code와 Sheet의 불일치를 세 유형으로 확인

    Source Code에만 있는 Missing Key, Sheet에만 남은 Unused Key, 여러 Tab의 Duplicated Key를 구분했습니다. Source File과 Sheet를 사람이 대조하는 방식으로는 누락을 안정적으로 찾거나 정리 상태를 유지하기 어렵다는 근거가 분명해졌습니다.

  3. Decision

    수동 대조와 정리를 개발 Workflow로 전환

    정리 업무를 다른 담당자에게 넘기는 대신, 개발팀에서 자동으로 실행할 수 있는 공용 CLI를 제안했습니다. Validation Result가 곧 Source Location과 Sheet Cleanup으로 이어지는 흐름을 기준으로 도구의 범위를 정했습니다.

  4. Execution

    AST Validation부터 Sheet Cleanup까지 자동화

    Babel AST로 실제 i18n Function Call만 추출해 Source Code와 Sheet의 Set Difference를 계산하고, Duplicated Key는 전역 Map으로 모아 값이 같은 중복만 자동 정리하고 값이 다른 중복은 확인 목록으로 남기도록 GitHub Actions Workflow에서 자동화했습니다. 완성한 CLI는 먼저 백오피스 프로젝트에 적용해 검증한 뒤 프론트·기획·디자인 팀에 직접 소개했고, GitHub Packages로 배포해 8개 프로젝트가 동일한 검증 규격을 그대로 재사용하게 되었습니다.
